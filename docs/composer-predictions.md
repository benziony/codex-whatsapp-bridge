# Composer suggestions through the existing third message

The Stop hook can turn the app-generated suggestion already mirrored as a
third message into an actionable WhatsApp suggestion. This is an opt-in local
integration; normal setup does not install the executable wrapper or restart
Codex.

## Exact source binding

The desktop starts composer predictions in temporary ephemeral threads. The
ordinary Stop payload identifies that temporary thread, so it cannot establish
the original chat by itself.

`scripts/codex-prediction-proxy.mjs` uses the desktop's executable override to
forward its existing app-server JSONL connection. It observes the successful
prediction fork and the subsequent turn-start source metadata. A private ledger
joins the temporary thread and turn to the original thread and source turn.
Connection-scoped request identities prevent collisions after restart or across
multiple app-server processes. No prediction is generated by the bridge.

The wrapper forwards stdin, stdout, stderr, arguments, exit status and signals.
Its ledger contains only routing identifiers and timestamps. It does not retain
prompts, responses, credentials, or protocol traffic. The ledger directory is
mode `0700`, its file is mode `0600`, and writes are locked and atomic. Capture
failure preserves the Codex transport; it cannot manufacture a bound suggestion.

The Stop hook uses only an exact ledger match. It never infers a binding from
arrival order, timestamps, chat titles, working directories, or inherited fork
history. An ordinary requested JSON answer containing a `suggestion` property
remains an ordinary answer when it has no trusted prediction binding.

## Approval and additions

The hook parses the bound prediction's existing JSON result. It applies the
same outer-whitespace trim as the app's suggestion parser, retaining all
interior text. A null or empty suggestion produces no action.

The broker sends the full suggestion followed by a native single-choice poll
with **Send suggestion** and **Dismiss**. Selecting Send suggestion queues the
stored suggestion unchanged. To add information, quote the suggestion message
and write the addition. The bridge submits:

```text
<exact suggestion>

<exact added text>
```

Attachments continue through the existing staged-input path. Poll and quoted
submissions share one atomic consumption record; use either the poll or a quote
for a given suggestion. Approving first and then quoting it does not create a
second submission.

The broker requires the exact original host, chat and source-turn record. It
rejects changed text under the same prediction identity, unauthorized votes
and quotes of partially delivered suggestions. Accepted-turn
recovery retains the existing stable request identity.

Definite message or poll failures resume through the existing client polling
loop. Poll retries retain their stable native delivery key. An uncertain full
message send is held for reconciliation instead of being sent again.

## Activation boundary

Before applying anything, inspect the installed app and CLI version, both hosts'
bridge releases, the exact current launch environment, and rollback settings.
Run the repository tests and setup dry run. Keep the reviewed executable and
ledger on the originating Mac; never copy live Codex or Hermes databases or
credentials between hosts.

The wrapper accepts these launch-environment values:

- `CODEX_CLI_PATH`: an executable launcher for this wrapper.
- `CODEX_PREDICTION_REAL_CLI_PATH`: the absolute bundled Codex executable to
  delegate to. It must not resolve to the wrapper itself.
- `CODEX_PREDICTION_BINDINGS_PATH`: optional absolute ledger path; its default is
  `~/.config/codex-whatsapp-bridge/prediction-bindings.json`. The Stop hook and
  wrapper must use the same path.

Use an executable launcher with the approved absolute Node path, rather than
assuming the desktop launch environment can resolve `node`. For example:

```sh
#!/bin/sh
export CODEX_PREDICTION_REAL_CLI_PATH='/absolute/path/to/bundled/codex'
export CODEX_PREDICTION_BINDINGS_PATH='/absolute/private/prediction-bindings.json'
exec '/absolute/path/to/node' '/absolute/bridge/scripts/codex-prediction-proxy.mjs' "$@"
```

The real child's `CODEX_CLI_PATH` is reset to the bundled executable to avoid
recursive helper interception. Non-app-server invocations delegate unchanged.
Activation requires a separately approved app launch-environment change and
restart. Rollback restores the prior environment and restarts the app using its
original executable; the existing bridge can continue ordinary turn mirroring.

## Remaining release boundaries

The third message is a generated candidate. The desktop can subsequently
suppress that candidate before displaying a composer chip. The wrapper proves
its original chat and exact generated text; it does not observe the desktop's
final display decision. Do not describe this as a verified export of only
visible composer chips.

Approving a suggestion targets its exact original chat even when that chat has
advanced. The source turn is provenance, not a submission precondition. If the
desktop still owns the chat, delivery uses the existing native queue with the
exact original thread ID and prompt. It does not require the desktop to release
its writer. Existing queue admission, uncertainty fencing, and recovery rules
prevent blind replay; an uncertain queue admission still requires reconciliation.

## Proof

Local deterministic tests cover the actual Stop CLI, real broker process and
loopback WhatsApp transport, exact source identities, native poll approval,
quoted additions after source advancement, desktop-owned native queue delivery,
ordinary JSON answers, abstention, persistence, authorization,
one-time consumption, uncertain sends, migration and native submission recovery.
The proxy fixture checks the full desktop argument shape, exact protocol bytes,
pre-forward metadata persistence and connection-scoped request-ID reuse.

These are local fixture results. Before claiming live completion, activate the
reviewed release and prove one approved suggestion, one quoted addition, one
accepted original-chat turn and its returned WhatsApp answer on every supported
originating host. Existing native permission and credential boundaries remain
intact.
